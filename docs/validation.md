# 検証記録

検証日: 2026-10-25（日本時間）

## 環境

Apple M3 Max / arm64、macOS 26.6.2、Xcode 26.6。deployment targetは26.0です。旧世代macOSとIntelは対応・検証対象外です。

## ビルド・単体テスト

- 初版と配布候補でarm64 Releaseビルド・Archiveが成功。
- `scripts/build.sh`の実行中アプリ検出、生成先コピー、起動先登録を実行確認。
- 更新機能追加後の`./scripts/test.sh`: 15件成功、失敗0。
- 実際の共有ソースをホストレスXCTestでコンパイル。縦横比・中央配置・空入力、画面外と巨大ウィンドウの補正、負座標、小さい指定倍率、保存設定と無効値補正、旧ストリームの遅延フレーム拒否を検証。
- 追加3件はHTTPSフィード設定と32バイト公開鍵、HTTP・資格情報付きURL・fragment等の拒否、欠落・不正長公開鍵の拒否。通常構成ではループバックHTTPも拒否。
- Releaseは最適化、Hardened Runtime有効、get-task-allowなし。Debugのローカルad-hoc署名はSparkle読み込みのためHardened Runtime無効。
- Sparkle 2.10.0をexact versionとPackage.resolvedで固定。ライセンスをアプリに同梱。
- アイコンは本プロジェクトのCoreGraphicsコードから生成。16〜1024ピクセルのicnsを確認。更新確認画面で青い2画面のアイコンを目視確認。

## GUI・実フレーム

以下の基本機能は初版とDeveloper ID署名候補で確認しました。更新の置換試験は後述の隔離アプリで行い、別の証拠として扱います。

- 内蔵Retina画面4112×2658、外部HDMI画面1920×1080の実フレームを取得し目視。
- 内蔵／外部選択、再試行、30／60 FPS・システム上限の操作。
- カーソルON／OFFで取得再開と実フレーム継続。すべてのカーソル形状の網羅試験ではない。
- 50／100／200％、縦横比調整、最前面、標準全画面への移行と復帰。
- 2倍Retinaの表示先で、1920×1080映像の50％は480×302ポイント、100％は960×572ポイント（高さにはタイトルバー32ポイントを含む）。
- 自アプリを取得対象から除外し、再帰映像が現れないことを目視。
- 通常終了・再起動で対象画面、位置・サイズ、FPS、カーソル、最前面を復元。

画面内容や他アプリのタイトルをログに記録せず、取得フレーム・個人のデスクトップ画像をディスクやGitへ保存していません。

## 外部画面の物理試験

Developer ID署名・公証済みのアイコン／更新機能追加前候補で、ユーザーの協力により確認しました。

1. ウィンドウを外部画面上へ移動。
2. ケーブルを抜くと、映像が停止・消去され、表示対象の選択案内が出る。ウィンドウが内蔵画面内へ回収される。
3. 再接続後、Displayから外部画面を選び直すと1920×1080の実フレーム取得が再開。
4. macOSの設定で1920×1080→1600×900へ変更し、1600×900の実フレーム取得を確認。1920×1080へ戻し、取得再開を確認。元の解像度へ復元済み。

## 連続動作

上記の公証済み候補を外部画面取得中に600.01秒観測しました。30秒ごとの21サンプルでプロセスが継続し、RSSは81.8125〜81.859375MiB、CPUのサンプル値は3.1〜4.8％でした。終了後も動く試験画像の更新を目視しています。

これは10分間の限定観測です。長期安定性・リークの不存在や、更新機能追加後の同じ負荷値を保証しません。実際の表示FPS、走査出力、遅延は計測していません。FPS指定は取得・描画の上限です。

## 権限と署名

初版のad-hoc再ビルドで、画面収録が設定上ONでも保存済み署名要件と不一致となり、拒否されました。ユーザーの明示承認で本アプリのScreenCapture権限だけをリセットし、本人が現在のアプリを追加・許可して復旧しました。他アプリの権限は変更していません。

Developer ID候補で、未許可時の英語案内・システム設定への導線・許可後の取得を確認。同一証明書・bundle IDの候補置換後も許可を維持しました。

アイコン／更新機能追加前候補はAppleの公証が受理され、staplerの検証とGatekeeperの`Notarized Developer ID`判定が成功しています。最終の更新対応アプリ・DMGの検証は末尾の追加結果欄に区別して記載しています。

## 更新機能の隔離試験

本体と別のbundle ID・アプリ名の`ExMonitorUpdateTest`を作成。通常の設定保存・終了・Sparkleの処理を共有し、`UPDATER_TESTING`だけでキャプチャ開始を抑止し、HTTPを127.0.0.1/localhostに限定して許可しました。本番にはHTTP例外を含めません。

署名鍵は本体と同じキーチェーンのアプリ専用鍵。旧build 1と新build 2は同じDeveloper IDで署名し、試験用DMGとフィードをEd25519署名しました。試験用アプリは公証していません。

- 同じbuild・古いbuild: 更新のインストールを提示しない。
- 新しいbuild: 英語の確認UI、版番号、アイコンを表示。
- 確認画面を閉じた場合: 旧実行ファイルのSHA256が一致し、置換しない。
- 署名済みXMLの本文を変更: フィード署名エラーで拒否。
- 正しく署名したフィードを維持し、DMGを変更: 更新署名エラーで拒否。旧実行ファイルを維持。
- 正常なDMG: Install Update→Install and Relaunchでbuild 2へ置換し再起動。置換後のInfo.plist、実行プロセス、コード署名を確認。
- FPS 30、最前面ON、ウィンドウの位置・サイズが更新後も復元。試験直前のdefaults exportは書き込み反映前のためFPS値が古く、UIで選択した期待値と終了後の保存値を照合した。
- 最前面ON・全画面の状態で更新確認を開き、操作可能。
- サーバー停止: 接続エラーを表示し、「最新版」と誤表示しない。
- 本体の公開用HTTPSフィード: 非公開リポジトリによる404を更新取得エラーとして表示。

公開HTTPSでの実更新は未検証です。リポジトリの公開設定は変更せず、GitHub Releaseも公開していません。匿名で利用可能な配信先と署名済みappcastを用意してから、公開経路で検証する必要があります。
